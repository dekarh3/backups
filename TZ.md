# 1. Общие положения

Настоящее ТЗ описывает систему централизованного резервного копирования на базе:

- **`restic`** — клиентский механизм создания резервных копий;
- **`rest-server`** — серверный HTTPS-приёмник данных `restic`;
- **`api.py`** — сервер управления, планировщик, очередь команд, учёт состояния;
- **`interface.py`** — web-интерфейс администратора;
- **PostgreSQL** — оперативное состояние системы;
- **INI-файлы** — статическая конфигурация.

Система работает в режиме **Append-only**.

Понятие **«полный бэкап»** не используется.

---

# 2. Архитектура системы

## 2.1. СХД-сервер

На сервере хранения данных работают:

1. **`rest-server`**  
   Принимает данные от `restic` по HTTPS в режиме `append-only`.

2. **`api.py`**  
   FastAPI-сервер на Python 3.8:
   - управляет клиентами;
   - хранит очередь команд;
   - планирует бэкапы;
   - проверяет репозитории;
   - выполняет сверку снапшотов и конфигурации;
   - управляет политиками хранения;
   - инициирует очистку незавершённых данных;
   - отправляет алерты.

3. **`interface.py`**  
   Web-интерфейс:
   - просмотр состояния;
   - управление бэкапами;
   - аварийный перезапуск клиентского стека;
   - запуск `prune`;
   - ротация секретов;
   - просмотр логов и алертов.

4. **PostgreSQL**  
   Хранит оперативное состояние:
   - команды;
   - запуски;
   - события;
   - снапшоты;
   - проверки;
   - алерты;
   - аудит.

5. **Серверные задачи обслуживания**
   - ежедневный мониторинг места;
   - ежедневная проверка целостности;
   - ежедневная сверка снапшотов;
   - применение политики хранения;
   - обязательный ежедневный `prune`.

---

## 2.2. Клиент

На каждом клиенте работают:

1. **`cerber.py`** — сторожевой процесс;
2. **`manager.py`** — управляющий агент;
3. **`worker.py`** — экземпляр процесса бэкапа;
4. **`restic`** — утилита резервного копирования.

Все клиентские скрипты реализуются на **Python 3.8**.

Версии `restic`:

- **Windows 7 Pro**: `restic 0.15.2`;
- **RedOS 8**: `restic 0.19.1`.

Клиент и сервер используют общий совместимый набор функций `restic`.

---

# 3. Основные принципы

## 3.1. Один репозиторий на каждый бэкап

Для каждого бэкапа каждого клиента создаётся отдельный репозиторий:

```text
/srv/backups/restic/<client>/<backup_name>/
```

URL репозитория:

```text
https://backup-srv:8443/<client>/<backup_name>
```

Это осознанный выбор архитектуры.

---

## 3.2. Клиент только пишет

Принят режим:

> Клиент только пишет.

Технически это означает:

- клиент может добавлять новые данные в репозиторий;
- клиент выполняет минимально необходимое чтение, требуемое для работы `restic backup`;
- клиент не выполняет административного чтения;
- клиент не выполняет восстановление;
- клиент не выполняет просмотр снапшотов в целях администрирования;
- восстановление выполняется только сервером.

---

## 3.3. Восстановление

Восстановление данных:

- выполняется только администратором;
- выполняется вручную;
- выполняется из консоли сервера;
- не предоставляется через клиент;
- не предоставляется через `interface.py`.

---

## 3.4. Модель доверия

Принята **Модель 1: сервер доверенный**.

Это означает:

- сервер знает пароли репозиториев `restic`;
- сервер может выполнять:
  - `restic snapshots`;
  - `restic check`;
  - `restic forget`;
  - `restic prune`;
  - `restic restore`;
- сервер выполняет обслуживание и восстановление.

Следствие:

- при компрометации сервера конфиденциальность данных не может быть гарантирована;
- для снижения риска применяются:
  - ограничение доступа;
  - аудит;
  - алерты;
  - ротация секретов;
  - резервное копирование конфигурации и ключей;
  - дополнительные меры защиты, описанные в разделе 18.

---

# 4. Серверная часть

## 4.1. `rest-server`

### 4.1.1. Режим работы

`rest-server` должен работать:

- только по HTTPS;
- в режиме `append-only`;
- с ограничением доступа по пользователям;
- с изоляцией клиентских репозиториев.

Клиент не может удалить или перезаписать уже принятые данные через `rest-server`.

---

### 4.1.2. Структура данных

Каталог хранения:

```text
/srv/backups/restic/<client>/<backup_name>/
```

Пример:

```text
/srv/backups/restic/ws01/documents/
/srv/backups/restic/ws01/postgres/
```

---

### 4.1.3. Аутентификация

Для каждого клиента создаётся отдельный пользователь `rest-server`.

Рекомендуемый файл пользователей:

```text
/opt/backups/auth/restic.htpasswd
```

Пароль пользователя хранится в отдельном секрете:

```text
/opt/backups/secrets/<client>.rest-http.pass
```

Права:

```text
0600
```

---

### 4.1.4. Управление пользователями `rest-server`

Управление пользователями выполняется `api.py`.

Механизм:

1. `api.py` программно редактирует `htpasswd`-файл.
2. Запись выполняется атомарно.
3. Перед изменением создаётся резервная копия файла.
4. Если `rest-server` не поддерживает горячую перезагрузку пользователей:
   - применяется перезапуск или перезагрузка сервиса;
   - перезапуск не выполняется, если есть активные бэкапы, кроме аварийных случаев.

---

## 4.2. `api.py`

### 4.2.1. Общие требования

`api.py`:

- реализуется на Python 3.8;
- работает в среде RedOS 8;
- использует FastAPI;
- использует PostgreSQL для оперативного состояния;
- использует INI-файлы для статической конфигурации.

---

### 4.2.2. Запуск

При старте `api.py` обязан:

1. Загрузить конфигурацию.
2. Проверить ключи подписи.
3. Проверить подключение к PostgreSQL.
4. Проверить доступность `rest-server`.
5. Проверить наличие репозиториев по конфигурации.
6. Проверить наличие пользователей `rest-server`.
7. Подключить клиентов.
8. Инициировать запрос состояния клиентов.
9. Проверить очередь команд.
10. Проверить задачи очистки и обслуживания.

---

### 4.2.3. Взаимодействие с клиентами
Взаимодействие `manager.py` и `api.py` осуществляется по протоколу HTTP/REST. Для получения команд используется механизм Long-Polling (клиент отправляет GET-запрос, сервер удерживает его до появления команды или истечения таймаута). Для отправки телеметрии, статусов и событий клиент использует асинхронные POST-запросы.

---

## 4.3. `interface.py`

### 4.3.1. Общие требования

`interface.py`:

- реализуется на Python 3.8;
- работает в среде RedOS 8;
- предоставляет web-интерфейс на базе FastAPI и шаблонизатора Jinja2 (Server-Side Rendering);
- взаимодействует с `api.py` (или является частью единого приложения FastAPI).

---

### 4.3.2. Роли

Роли:

1. **администратор**;
2. **наблюдатель**.

---

### 4.3.3. Права ролей

#### Администратор

Может:

- просматривать состояние;
- просматривать логи;
- запускать и останавливать бэкапы;
- выполнять `client.stack.restart`;
- выполнять `abort_cleanup`;
- выполнять `prune`;
- запускать ротацию секретов;
- изменять конфигурацию.

#### Наблюдатель

Может:

- просматривать состояние;
- просматривать логи;
- просматривать алерты.

Не может:

- выполнять управляющие команды;
- изменять конфигурацию;
- запускать очистку;
- выполнять ротацию секретов.

---

### 4.3.4. Аутентификация и доступ

Требования:

- вход с 2FA по почте;
- ограничение доступа по IP;
- подтверждение опасных операций только предупреждением на экране;
- аудит действий в логе.

---

### 4.3.5. Индикация

Интерфейс должен показывать:

- состояние клиента;
- состояние каждого бэкапа;
- прогресс;
- время последнего контакта;
- статус `long_running`;
- ошибки;
- алерты;
- результат проверок;
- состояние дискового пространства.

Правила индикации:

- клиент считается онлайн, если последний контакт был менее 2 минут назад;
- предупреждение о потере контакта выводится через 2 минуты;
- ошибка потери контакта выводится через 5 минут.

Для активного бэкапа подтверждением работы считается обращение клиента к `rest-server`.

# 5. Конфигурация

## 5.1. Файлы конфигурации

Статическая конфигурация хранится в INI-файлах.

Основной файл:

```text
/opt/backups/ini/backups.ini
```

Клиенты:

```text
/opt/backups/ini/clients/<client>.ini
```

Бэкапы:

```text
/opt/backups/ini/backups/<client>.<backup_name>.ini
```

Календарь рабочих и праздничных дней:

```text
/opt/backups/ini/calendar.ini
```

---

## 5.2. Оперативное состояние

Оперативное состояние хранится в PostgreSQL.

В PostgreSQL хранятся:

- очередь команд;
- состояния команд;
- запуски бэкапов;
- события;
- снапшоты;
- результаты проверок;
- задачи очистки;
- алерты;
- аудит;
- версии агентов и скриптов.

---

## 5.3. Источники истины

| Ситуация | Источник истины |
|---|---|
| В `api.py` бэкап отмечен как успешный, но снапшота нет | снапшот |
| Снапшот есть, но `api.py` о нём не знает | снапшот |
| Репозиторий существует, но конфигурация удалена | конфигурация |
| Конфигурация есть, но репозиторий удалён вручную | конфигурация |

Дополнительно:

- `api.py` раз в сутки сканирует `restic snapshots`;
- при расхождении:
  - отправить письмо;
  - показать в `interface.py`;
- неизвестные снапшоты для существующих конфигураций автоматически импортируются в учёт;
- осиротевшие репозитории автоматически не удаляются;
- об осиротевших репозиториях выводится информация в интерфейс и отправляется письмо.

## 5.8. Календарь рабочих и праздничных дней

Календарь хранится в INI-файле.

Формат дат:

```text
DD.MM.YYYY
```

Пример:

```ini
[calendar]
working_weekend_days = 05.01.2026, 06.01.2026
holiday_days = 01.01.2026, 07.01.2026, 09.05.2026
```

Формула рабочего дня:

1. Дни с понедельника по пятницу считаются рабочими.
2. Если дата входит в список `working_weekend_days`, она считается рабочим днём.
3. Если дата входит в список `holiday_days`, она считается выходным днём.

Календарь используется для служебных расчётов и может использоваться в политиках, если это явно задано конфигурацией.
Если в конфигурации бэкапа указан параметр `respect_calendar = true`, планировщик `api.py` пропускает плановый запуск бэкапа в выходные и праздничные дни (согласно `calendar.ini`), кроме дней, отмеченных как рабочие выходные.

# 6. Команды управления

## 6.1. Удалённые команды

Из системы исключены:

- `manager.hello`;
- `manager.<backup_name>.delete_backup`;
- `manager.<backup_name>.delete_all_backups`.

---

## 6.2. Поддерживаемые команды

### Общие

- `manager.status` — запрос состояния клиента и бэкапов;
- `manager.config` — обновление конфигурации клиента;
- `manager.<backup_name>.script` — обновление скрипта бэкапа.

### Управление бэкапом

- `manager.<backup_name>.start` — запустить бэкап;
- `manager.<backup_name>.stop` — остановить бэкап;
- `manager.<backup_name>.restart` — остановить и перезапустить бэкап;
- `manager.<backup_name>.abort_cleanup` — остановить бэкап и очистить незавершённые данные.

### Аварийный перезапуск клиентского стека

- `client.stack.restart` — аварийный перезапуск клиентского стека.

---

## 6.3. Состояния команды

Команда может находиться в состояниях:

```text
created
pending
delivered
ack_received
running
success
failed
expired
cancelled
```

---

## 6.4. Срок жизни команды

Базовый срок жизни команды:

```ini
command_ttl_hours = 12
```

Правила:

1. Команда создаётся в состоянии `created`.
2. Если команда не доставлена клиенту, она может ожидать доставки в пределах:

```ini
offline_grace_hours = 6
```

3. Если клиент появился онлайн в течение 6 часов, команда доставляется.
4. Если клиент не появился в течение 6 часов, команда устаревает.
5. Если команда уже доставлена, подтверждена или выполняется, применяются таймауты исполнения.
6. При истечении срока:
   - если команда связана с активным процессом — процесс останавливается;
   - выполняется очистка незавершённых данных;
   - команда переводится в `expired`.

Для устранения конфликта с длительным бэкапом вводится отдельное правило:

- 3 часа — срок доставки, подтверждения и старта;
- 12 часов — максимальное время выполнения самого бэкапа.

---

## 6.5. Отмена команды

Команду можно отменить.

При отмене:

- если команда ещё не выполнялась — она переводится в `cancelled`;
- если команда уже выполняется:
  - процесс останавливается;
  - выполняется очистка незавершённых данных;
  - команда переводится в `cancelled`.

---

## 6.6. Повторные попытки и подтверждения

### 6.6.1. Клиент подтвердил получение, но исполнение не началось

Параметры:

```ini
ack_timeout_minutes = 10
ack_retry_max = 10
```

Поведение:

1. Ожидание 10 минут.
2. Повтор команды.
3. Максимум 10 повторов.
4. Если исполнение не началось:
   - выполняется очистка;
   - команда переводится в `failed`.

---

### 6.6.2. Клиент выполнил, но не смог подтвердить

Поведение:

1. Система проверяет фактическое состояние бэкапа.
2. Проверка выполняется по:
   - наличию снапшота с соответствующим `run_id`;
   - состоянию агента;
   - журналам запуска.
3. Если результат подтверждён:
   - команда переводится в `success`.
4. Если результат не подтверждён:
   - выполняется очистка;
   - выполняется повтор;
   - максимум повторов:

```ini
run_missing_ack_retry_max = 2
```

5. Если повторы исчерпаны:
   - выполняется очистка;
   - команда переводится в `failed`.

---

## 6.7. Предотвращение повторного выполнения

Используются:

- уникальный `command_id`;
- уникальный `run_id` для запусков бэкапа;
- локальный реестр выполненных `command_id` на клиенте;
- проверка активного состояния бэкапа на сервере и клиенте.

Клиент не выполняет команду повторно, если такой `command_id` уже обработан.

---

## 6.8. Идемпотентность команд

### `start`

Если бэкап уже выполняется:

- новый процесс не запускается;
- событие игнорируется;
- запись отражается в логе.

Если команда с таким `command_id` уже выполнена:

- повторный запуск не производится.

---

### `stop`

Если бэкап выполняется:

- процесс останавливается.

Если бэкап не выполняется:

- команда завершается успешно как `already_stopped`.

---

### `restart`

Если бэкап выполняется:

- остановить;
- очистить незавершённые данные;
- запустить новый процесс с новым `run_id`.

Если бэкап не выполняется:

- запустить новый процесс.

---

### `abort_cleanup`

Если процесс выполняется:

- остановить;
- выполнить очистку.

Если процесс не выполняется:

- поставить серверную задачу очистки незавершённых данных, если она ещё не поставлена.

Повторный вызов не создаёт вторую задачу очистки.

---

## 6.9. Команда `client.stack.restart`

Назначение:

- применяется, если клиентский стек полностью завис.

Выполняется:

- только из `interface.py`;
- только администратором;
- только с подтверждением.

Действие:

1. Активные бэкапы останавливаются.
2. Незавершённые данные очищаются.
3. Процессы завершаются принудительно:
   - `manager.py`;
   - все `worker.py`;
   - все процессы `restic`, запущенные агентом.
4. Запускается заново клиентский стек:
   - `manager.py`;
   - связанные рабочие процессы при необходимости.

Способ завершения процессов:

- `kill`;
- на Windows — принудительное завершение дерева процессов.

Команда не выполняет перезагрузку операционной системы.

---

## 6.10. Команда `abort_cleanup`

Команда означает:

- остановить бэкап на клиенте;
- удалить незавершённые данные на СХД.

Технически:

1. На клиенте:
   - останавливается `worker.py`;
   - останавливается процесс `restic`;
   - удаляются локальные временные файлы, если они создавались скриптом.

2. На СХД:
   - создаётся серверная задача очистки незавершённых данных;
   - очистка выполняется через `restic prune`;
   - если репозиторий свободен, очистка может быть выполнена вне очереди;
   - если репозиторий занят, очистка откладывается до освобождения или до обязательного ежедневного `prune`.

Завершённые снапшоты при этом не удаляются.

---

# 7. Клиентская часть

## 7.1. Общие требования

Клиентские компоненты:

- реализуются на Python 3.8;
- работают под выделенным служебным пользователем;
- поддерживают:
  - RedOS 8;
  - Windows 7 Pro.

---

## 7.2. `cerber.py`

`cerber.py`:

- является сторожевым процессом;
- контролирует `manager.py`;
- участвует в аварийном перезапуске стека;
- участвует в обновлении агента.

---

## 7.3. `manager.py`

`manager.py`:

- получает команды от `api.py`;
- управляет конфигурацией;
- запускает и останавливает `worker.py`;
- контролирует состояние бэкапов;
- передаёт статус на сервер;
- после сбоя пытается переподключиться к уже запущенному `restic`.

---

## 7.4. `worker.py`

`worker.py`:

- создаётся один на бэкап;
- выполняет запуск бэкапа;
- следит за процессом `restic`;
- передаёт события и прогресс;
- обрабатывает ошибки;
- очищает временные данные при остановке.

---

## 7.5. Локальные служебные каталоги

### Linux

```text
/opt/backups-agent/scripts/
/var/lib/backups-agent/run/
/var/log/backups-agent/
/backup_cache/restic/
```

### Windows

```text
C:\ProgramData\backups-agent\scripts\
C:\ProgramData\backups-agent\run\
C:\ProgramData\backups-agent\logs\
B:\restic_cache\
```

Если отдельный диск для кэша не выделен, путь к кэшу задаётся в конфигурации.

---

## 7.6. PID-файлы и флаг-файлы процессов

Для каждого запуска создаются служебные файлы:

Пример для Linux:

```text
/var/lib/backups-agent/run/<client>.<backup>.<run_id>.pid
/var/lib/backups-agent/run/<client>.<backup>.<run_id>.state
/var/lib/backups-agent/run/<client>.<backup>.<run_id>.log
```

Содержимое `.pid`-файла:

- PID `worker.py`;
- PID `restic`;
- PID скрипта бэкапа, если он отдельный;
- `run_id`;
- время старта.

При сбое:

- удаляется не только дерево процессов;
- дополнительно завершаются отдельные процессы, указанные в PID-файлах.

---

## 7.7. Блокировка одновременного запуска

Для каждого бэкапа используется локальный lock-файл:

```text
/var/lib/backups-agent/run/<client>.<backup>.lock
```

или для Windows:

```text
C:\ProgramData\backups-agent\run\<client>.<backup>.lock
```

Механизм:

1. Перед стартом создаётся lock-файл атомарно.
2. В него пишутся:
   - `run_id`;
   - PID;
   - время старта.
3. Если lock-файл уже существует:
   - проверяется живой ли процесс;
   - если процесс жив — запуск не выполняется;
   - если процесс мёртв — выполняется очистка и запуск.
4. Одновременный запуск одного и того же бэкапа не допускается.

---

## 7.8. Переподключение `manager.py` к существующему `restic`

Если `manager.py` перезапустился во время активного бэкапа:

1. `manager.py` читает PID-файлы и `.state`-файлы.
2. Проверяет тип скрипта бэкапа (указанный в конфигурации) и жив ли процесс `restic`.
3. Если `script_mode` не `pipe` и процесс жив:
   - `manager.py` переподключается к мониторингу;
   - чтение прогресса выполняется из журнала запуска;
   - статус остаётся `running`.
4. Если `script_mode` равен `pipe` или процесс мёртв:
   - выполняется очистка;
   - применяется политика перезапусков.

Для возможности переподключения вывод `restic` должен писаться в журнал запуска.

---

## 7.9. Поведение при падении `worker.py`

Если `worker.py` падает:

1. Выполняется очистка незавершённых данных.
2. Выполняется перезапуск.
3. Повторов до 5 раз.
4. Интервалы:

```ini
retry_intervals_minutes = 5,15,30,30,30
```

5. Если после 5 попыток бэкап не выполнен:
   - передаётся статус `failed`;
   - выполняется очистка незаписанных/незавершённых данных;
   - бэкап помечается как ошибочный.

---

## 7.10. Таймауты

Параметры:

```ini
api_connect_timeout_minutes = 5
restic_start_timeout_minutes = 10
progress_timeout_minutes = 2
script_prepare_timeout_sec = 600
stop_timeout_minutes = 5
```

Значения:

- таймаут подключения к API — 5 минут;
- таймаут запуска `restic` — 10 минут;
- таймаут отсутствия прогресса — 2 минуты;
- таймаут подготовки скрипта — 600 секунд;
- таймаут завершения процесса — 5 минут.

---

## 7.11. Остановка процесса

Порядок остановки:

1. Послать `SIGINT`.
2. Ждать 5 минут.
3. Если процесс не завершился — выполнить принудительное завершение.

Для Windows:

1. Послать прерывание процессу, если это возможно.
2. Ждать 5 минут.
3. Если процесс не завершился — убить дерево процессов.

Если `restic` завис:

- процессы убиваются принудительно.

---

## 7.12. Незавершённый снапшот

Если `restic` остановлен аварийно:

- финальный снапшот не создаётся;
- в репозитории могут остаться загруженные, но не привязанные к снапшоту данные;
- такие данные считаются незавершёнными;
- очистка выполняется сервером.

---

## 7.13. `restic unlock`

Сервер не выполняет `restic unlock` вслепую. Если требуется принудительное снятие блокировки, сервер сначала отправляет клиенту команду `abort_cleanup` или `client.stack.restart`, чтобы гарантированно завершить процессы `restic` на стороне клиента. Только после получения от клиента подтверждения, что PID процесса `restic` отсутствует, сервер выполняет `restic unlock`.

---

# 8. Скрипт бэкапа

## 8.1. Общие требования

Скрипт бэкапа:

- реализуется на Python 3.8;
- запускается `worker.py`;
- не должен выводить секреты;
- должен завершаться с кодом 0 при успехе;
- должен работать не дольше:

```ini
backup_prepare_timeout_sec
```

Пути и данные для бэкапа определяются внутри скрипта.

---

## 8.2. Формат скрипта

Режим работы скрипта задаётся параметром `script_mode` в конфигурации бэкапа (допустимые значения: `pipe` или `file`). Указание режима необходимо для корректной работы механизма переподключения `manager.py` (см. п. 7.8).

Основной формат:

> Скрипт бэкапа — это Python-скрипт, который передаёт данные в `restic` через конвейр.

Незашифрованные промежуточные файлы на диск не пишутся.

Дампы баз данных:

- не создаются на диске;
- передаются в `restic` через pipe;
- шифруются уже внутри `restic`.

---

## 8.3. Варианты работы скрипта

### 8.3.1. Потоковый режим (`script_mode = pipe`)

Скрипт формирует поток данных и передаёт его в `restic`.

Примерный принцип:

```python
import subprocess

dump = subprocess.Popen(
    ["pg_dump", "-U", "backup_user", "mydb"],
    stdout=subprocess.PIPE
)

restic = subprocess.Popen(
    [
        "restic", "backup",
        "--stdin",
        "--stdin-filename", "mydb.sql",
        "--tag", "client=ws01",
        "--tag", "backup=postgres",
        "--tag", "run_id=..."
    ],
    stdin=dump.stdout
)

dump.stdout.close()
restic.wait()
```

Незашифрованный дамп существует только в памяти/конвейере.

---

### 8.3.2. Файловый режим (`script_mode = file`)

Если бэкапятся файлы, скрипт может вызывать `restic backup` с путями, которые определяются внутри скрипта.

Пример:

```python
import subprocess

paths = [
    "/data/documents",
    "/data/user_profiles",
]

cmd = [
    "restic", "backup",
    "--tag", "client=ws01",
    "--tag", "backup=documents",
    "--tag", "run_id=..."
]

cmd.extend(paths)

subprocess.run(cmd, check=True)
```

---

## 8.4. Требования к выводу

Скрипт:

- не должен печатать секреты;
- может печатать служебную информацию в лог;
- обязан вернуть код завершения `0` при успехе;
- при ошибке вернуть ненулевой код.

---

## 8.5. Версия скрипта

Каждый скрипт имеет версию.

Перед каждым запуском бэкапа:

1. `manager.py` сверяет версию скрипта с ожидаемой.
2. Если версия старая:
   - запускается обновление;
   - после успешного обновления выполняется запуск бэкапа.
3. Если обновление не удалось:
   - бэкап не запускается;
   - отправляется алерт.

---

# 9. Выполнение бэкапа

## 9.1. Расписание

Для каждого бэкапа задаётся одно расписание:

```ini
schedule = 0 22 * * *
```
---

## 9.2. Запуск

`api.py` создаёт команду `start`, если:

- бэкап включён;
- клиент онлайн;
- никакие бэкапы в этом репозитории не находятся в состоянии `running`;
- нет нарушений лимитов;
- версия скрипта и агента актуальна.

---

## 9.3. Лимит снапшотов

Устанавливается лимит:

```ini
snapshot_daily_limit = 2
snapshot_8h_limit = 1
```

Правило:

- не более двух успешных снапшотов в сутки на бэкап.
- не более одного успешного снапшота за 8 часов

Если два успешных снапшота за текущие сутки или один успешный снапшот за последние 8 часов уже есть:

- новый плановый запуск пропускается;
- событие отражается в логе и интерфейсе.

---

## 9.4. Длительные бэкапы

Параметры:

```ini
long_running_threshold_hours = 3
max_run_time_hours = 12
```

Поведение:

1. Если бэкап выполняется более 3 часов:
   - статус `long_running`;
   - показать в `interface.py`.

2. Если бэкап выполняется более 12 часов:
   - остановить бэкап;
   - удалить незавершённые данные;
   - показать в `interface.py`;
   - отправить письмо.

3. Пока бэкап выполняется:
   - параллельный запуск того же бэкапа не выполняется;
   - повторяющиеся команды `start` игнорируются и пишутся в лог.

---

## 9.5. Повторные попытки

Интервалы повторов:

```ini
retry_intervals_minutes = 5,15,30,30,30
```

Это означает до 5 попыток:

1. через 5 минут;
2. через 15 минут;
3. через 30 минут;
4. через 30 минут;
5. через 30 минут.

---

## 9.6. Классификация ошибок
Для классификации ошибок `worker.py` анализирует код завершения (exit code) процесса `restic` и парсит текстовый вывод из `stderr`. 
- Сетевые ошибки определяются по ключевым словам в `stderr` (например, `connection refused`, `timeout`). 
- Ошибки доступа — по маркерам `401 Unauthorized`, `wrong password`, `permission denied`.
- Ошибки скрипта определяются по ненулевому коду завершения самого Python-скрипта до старта `restic` или `exit code 1` без сетевых маркеров.
- Ошибки доступа и скрипта не повторяются.

### Сетевые ошибки

- повтор до 5 раз;
- интервалы 5, 15, 30, 30, 30 минут.

### Ошибки доступа

- без повторов;
- статус `failed`.

### Ошибки скрипта

- без повторов;
- статус `failed`.

---

## 9.7. Недоступность `rest-server` и `api.py`

Если во время бэкапа исчезли одновременно:

- `rest-server`;
- `api.py`;

поведение:

- повтор до 5 раз с интервалами 5, 15, 30, 30, 30 минут;
- локальная очередь событий не ведётся;
- бэкапы стартуются только из `api.py`.

Локально могут храниться только служебные файлы состояния процесса:

- PID-файлы;
- lock-файлы;
- журналы запуска.

---

## 9.8. Кэш `restic`

Параметры:

```ini
restic_cache_root = /backup_cache
restic_cache_max_gb = 1024
restic_allow_no_cache = true
```

Требования:

- кэш хранится на отдельном диске;
- максимальный размер кэша — 1 ТБ;
- при переполнении клиентского диска бэкап пишется без кэша;
- работа без кэша разрешена.

Реализация:

- использовать `--cache-dir`;
- при недоступности/переполнении кэша использовать `--no-cache`.

---

## 9.9. Теги снапшотов

Каждый снапшот должен содержать теги:

```text
client=<client>
backup=<backup_name>
run_id=<run_id>
```

# 10. Хранение, квоты, целостность и очистка

## 10.1. Формулировка Append-only, квоты и целостности

Режим `append-only` гарантирует, что клиент через `rest-server` не может удалить или перезаписать уже принятые данные.

Дополнительно защита обеспечивается:

- файловыми квотами;
- ограничением количества снапшотов;
- контролем аномального роста;
- мониторингом свободного места;
- проверкой целостности репозиториев;
- серверными операциями очистки.

---

## 10.2. Квоты

Параметр квоты (`quota_gb` или `quota_mb`) является **обязательным** для каждого бэкапа. При его отсутствии в конфигурации бэкап не стартует, генерируется алерт об ошибке конфигурации.

Поскольку стандартный `rest-server` не поддерживает встроенные квоты, контроль квот осуществляется на уровне `api.py`. Перед стартом бэкапа `api.py` проверяет фактический размер репозитория на диске на уровне файловой системы сервера (например, через `du -s /srv/backups/restic/<client>/<backup>` или `os.stat`). 
Если размер превышает квоту, бэкап не стартует, генерируется алерт. В качестве жёсткого барьера (hard limit) на уровне ОС рекомендуется использовать файловые квоты (Linux `quota` / Windows NTFS Disk Quotas) на каталог репозитория.

Квота задаётся в конфигурации бэкапа:

```ini
quota_gb = 500
```

или:

```ini
quota_mb = 512000
```

---

## 10.3. Мониторинг свободного места

Раз в сутки `api.py` проводит мониторинг свободного места.

Параметры:

```ini
free_space_stop_factor = 0.05
free_space_alert_factor = 0.1
```

Правила:

1. Вычисляется сумма всех квот всех бэкапов.
2. Если остаток свободного места меньше 5% от суммы всех квот:
   - выполняется автоматическая остановка бэкапов;
   - новые запуски не выполняются.
3. Если остаток свободного места меньше 10% от суммы всех квот:
   - выводится алерт в `interface.py`;
   - отправляется письмо администратору.

---

## 10.4. Аномальный рост

Правило:

- если новый успешный снапшот больше предыдущего успешного снапшота того же бэкапа более чем в 2 раза:
  - показать предупреждение в интерфейсе;
  - отправить письмо.

Параметр:

```ini
anomaly_growth_factor = 2.0
```

Автоматическая блокировка клиента не выполняется.

---

## 10.5. Формула хранения

Для каждого бэкапа применяется следующая формула:

1. Хранить все успешные снапшоты за последние 31 день.

2. Для каждого из последних 12 календарных месяцев:
   - если есть успешный снапшот в последний календарный день месяца — хранить его;
   - иначе хранить:
     - последний успешный снапшот до конца месяца и последующий успешный снапшот после конца месяца.

3. Если одного из двух снапшотов нет, хранится существующий.

4. Всё остальное отметить к удалению через `restic forget`.

5. Удаление устаревших снапшотов выполняется только при наличии более нового успешного снапшота для того же бэкапа, если политика не требует иного.

---

## 10.6. Связь между `forget` и `prune`

Правила:

- `prune` никогда не запускается автоматически сразу после каждого `forget`;
- `prune` может быть отложен;
- `prune` обязателен не реже одного раза в сутки;
- `prune` логируется в лог репозитория;
- при ошибке `prune`:
  - вывести предупреждение в `interface.py`;
  - отправить письмо администратору.

Дополнение:

- внеочередной `prune` допускается только для очистки незавершённых данных после:
  - `abort_cleanup`;
  - принудительной остановки по таймауту;
  - аварийного завершения процесса;
- если в репозитории есть активные бэкапы, выполнение `prune` ставится в очередь и выполняется сразу после окончания текущего бэкапа;
- во время выполнения `prune` бэкапы не стартуются.

---

## 10.7. Проверка целостности

`api.py` ежедневно выполняет проверку репозиториев.

Уровни проверки:

1. Ежедневно:
   - проверка метаданных репозитория через `restic check`;
   - проверка наличия успешных снапшотов.

2. Еженедельно:
   - выборочное чтение данных, например:

```bash
restic check --read-data-subset=1%
```

3. Ежемесячно:
   - более глубокая проверка для критичных репозиториев, вплоть до:

```bash
restic check --read-data
```

Если проверка выявила ошибку:

- бэкап помечается как ошибочный;
- показать в `interface.py`;
- отправить письмо администратору.

Важно:

`restic check` без чтения данных проверяет метаданные и структуру, но не гарантирует физическую читаемость всех данных.

---

## 10.8. Сверка снапшотов

Раз в сутки `api.py` сканирует:

```bash
restic snapshots --json
```

Правила:

- неизвестные снапшоты автоматически импортируются;
- осиротевшие репозитории не удаляются;
- при расхождениях:
  - письмо;
  - запись в `interface.py`.

# 11. Мониторинг, алерты и логи

## 11.1. Последний контакт

Последний контакт клиента определяется по любому из событий:

- событие от `worker.py`;
- статус от `manager.py`;
- подтверждение команды;
- любое другое зарегистрированное взаимодействие клиента с сервером.

Пороги:

```ini
contact_warning_minutes = 2
contact_error_minutes = 5
```

Правила:

- клиент онлайн, если последний контакт был менее 2 минут назад;
- предупреждение — через 2 минуты;
- ошибка — через 5 минут.

---

## 11.2. Подтверждение работы активного бэкапа

Для активного бэкапа подтверждением работы считается обращение клиента к `rest-server`.

Источники:

- журнал доступа `rest-server`;
- reverse proxy access log;
- метрики `rest-server`, если доступны.

Если во время активного бэкапа нет обращений к `rest-server`:

- через 2 минуты — предупреждение;
- через 10 минут — ошибка.

*Примечание: для активного бэкапа 10-минутный порог ошибки отсутствия обращений к `rest-server` перекрывает общий 5-минутный порог потери связи с `api.py` (описанный в п. 11.1), так как агент может быть полностью занят передачей данных и не отправлять статусы в API.*

---

## 11.3. Расхождение состояния

Если сервер считает бэкап запущенным, а клиент сообщает, что процесс не выполняется:

- прав клиент;
- запись о запуске автоматически останавливается в базе;
- при наличии основания для запуска выполняется перезапуск;
- событие отражается в логе и интерфейсе.

---

## 11.4. Обязательные алерты

Минимальный набор:

1. Бэкап завершился ошибкой.
2. Бэкап не выполнялся дольше ожидаемого срока.
3. Бэкап находится в состоянии `long_running`.
4. Бэкап остановлен по превышению 12 часов.
5. Проверка целостности завершилась с ошибкой.
6. Обнаружено расхождение между снапшотами и учётом.
7. Обнаружен осиротевший репозиторий.
8. Свободное место на СХД составляет менее 5% от суммы всех квот.
9. Свободное место на СХД составляет менее 10% от суммы всех квот.
10. Клиент недоступен более 5 минут.
11. Команда завершилась ошибкой.
12. Обнаружен аномальный рост снапшота.
13. Ошибка `prune`.
14. Ошибка ротации секретов.
15. Обновление агента завершилось ошибкой.

Каналы:

- `interface.py`;
- почта.

# 12. Безопасность

## 12.1. Модель угроз

Система должна защищаться от:

- вредоносного клиента;
- компрометации клиента;
- компрометации сервера;
- утечки данных;
- шифровальщика на клиенте.

Ограничение:

- при компрометации сервера полная защита данных не гарантируется, так как сервер доверенный и знает пароли репозиториев.

---

## 12.2. Первичная установка клиента

Первичная установка секретов выполняется вручную администратором на клиенте.

Используется локальный скрипт:

```text
bootstrap_client.py
```

Скрипт:

1. Запускается администратором.
2. Получает одноразовый регистрационный токен.
3. Подключается к `api.py`.
4. Получает:
   - пользователя `rest-server`;
   - пароль `rest-server`;
   - пароль репозитория;
   - открытый ключ сервера;
   - агентский токен или клиентский сертификат.
5. Сохраняет секреты в защищённое локальное хранилище.

---

## 12.3. Проверка сервера клиентом
Для аутентификации на `api.py` клиент использует агентский токен, передаваемый в HTTP-заголовке `Authorization: Bearer <token>`.
Для аутентификации на `rest-server` используется HTTP Basic Auth с логином и паролем из конфигурации. TLS-сертификаты серверов валидируются на клиенте через предустановленный корневой сертификат внутреннего CA.
  
Клиент проверяет сервер двумя способами:
1. Проверка TLS-сертификата `rest-server`:
   - используется доверенный внутренний CA;
   - корневой сертификат устанавливается на клиент.
2. Проверка подписи команд:
   - команды подписываются закрытым ключом `api.py`;
   - клиент проверяет подпись открытым ключом сервера;
   - открытый ключ сервера устанавливается при первоначальной установке.

Рекомендуется:

- использовать `key_id` в названии ключа;
- поддерживать два активных серверных ключа во время ротации;
- при смене ключа клиент должен подтвердить переход.

---

## 12.4. Ротация секретов

Ротация выполняется:

- из `interface.py`;
- раз в год;
- или при компрометации.

Ограничение:

- если есть активные бэкапы, механизм ротации недоступен.

---

### 12.4.1. Ротация пароля `rest-server`

Порядок:

1. Сгенерировать новый пароль.
2. Обновить `htpasswd`.
3. Доставить новый пароль клиенту через подписанную конфигурацию.
4. Дождаться подтверждения клиента.
5. Удалить старый пароль.

---

### 12.4.2. Ротация агентского токена или клиентского сертификата

Порядок:

1. Выпустить новый токен/сертификат.
2. Доставить клиенту.
3. Подтвердить успешную аутентификацию.
4. Отозвать старый токен/сертификат.

---

### 12.4.3. Ротация пароля репозитория

Варианты:

#### Рекомендуемый вариант

Создать новый репозиторий для будущих бэкапов:

- старый репозиторий остаётся архивным;
- новые бэкапы пишутся в новый репозиторий;
- клиент получает новый пароль и новый репозиторий.

#### Альтернативный вариант

Если версия `restic` поддерживает управление ключами:

1. Добавить новый ключ в репозиторий.
2. Доставить новый пароль клиенту.
3. Проверить успешный бэкап новым паролем.
4. Удалить старый ключ.

---

## 12.5. Защита секретов на клиенте

### Linux

Каталог секретов:

```text
/opt/backups-agent/secrets/
```

Права:

```text
каталог: 0700
файлы: 0600
владелец: пользователь агента
```

Дополнительно:

- отдельный пользователь;
- запрет общего доступа;
- по возможности шифрование диска.

### Windows

Каталог секретов:

```text
C:\ProgramData\backups-agent\secrets\
```

Требования:

- ограничить ACL:
  - `SYSTEM`;
  - `Administrators`;
  - пользователь службы агента;
- использовать DPAPI в контексте пользователя службы;
- не хранить секреты в открытом виде в реестре;
- не выводить секреты в логи.

---

## 12.6. Действия при компрометации клиента

При компрометации клиента:

1. Отозвать доступ клиента на сервере.
2. Заблокировать команды клиента.
3. Сменить пароль репозитория или перевести бэкап в новый репозиторий.
4. Выполнить повторную установку секретов вручную скриптом на клиенте.
5. Проверить репозиторий на аномалии.

# 13. Обновление агентов и скриптов

## 13.1. Версии

Каждый клиент имеет:

- версию `cerber.py`;
- версию `manager.py`;
- версию `worker.py`;
- версии скриптов бэкапов.

Сервер хранит ожидаемые версии в конфигурации и в базе.

---

## 13.2. Проверка перед запуском

Перед каждым запуском бэкапа:

1. Проверяется версия скрипта.
2. Проверяется версия агентских компонентов.
3. Если версия старая:
   - запускается обновление;
   - после успешного обновления выполняется запуск бэкапа.
4. Если обновление не удалось:
   - запуск не выполняется;
   - отправляется алерт.

---

## 13.3. Механизм обновления

Обновление распространяется централизованно через `api.py`.

Состав обновления:

- файлы агента;
- хэш-суммы;
- цифровая подпись сервера;
- версия.

Порядок:

1. Агент получает информацию о доступной версии.
2. Скачивает пакет обновления.
3. Проверяет подпись и хэши.
4. Распаковывает пакет во временный каталог.
5. `cerber.py` останавливает агентский стек.
6. Файлы заменяются.
7. Агентский стек запускается.
8. Агент подтверждает новую версию.

Ограничения:

- если есть активные бэкапы, обновление откладывается;
- принудительное обновление возможно только с подтверждением администратора;
- сохраняется предыдущая версия для отката;
- при замене файлов (особенно в ОС Windows) `cerber.py` обязан убедиться, что файловые дескрипторы освобождены (проверить отсутствие процесса в памяти через `psutil` или аналогичный механизм), и только затем выполнять перезапись.

# 15. Аварийное восстановление сервера

## 15.1. Архив конфигурации и секретов

Скрипт из-под root создаёт зашифрованный архив:

```text
/backups/restic_YYYY-MM-DD.7z
```

Пароль архива хранится в:

```text
/root/.backup_password
```

Архив должен содержать файлы с абсолютными путями:

- пароли репозиториев;
- ключи подписи;
- конфигурацию;
- сервисы;
- `api.py`;
- актуальный дамп PostgreSQL.

Актуальный дамп PostgreSQL создаётся ежедневно по cron (например, через `pg_dump`), при этом прошлая версия дампа замещается новой. Скрипт архивации упаковывает этот свежий дамп в итоговый 7z-архив.

Рекомендуемый состав:

```text
/opt/backups/ini/
/opt/backups/secrets/
/opt/backups/keys/
/opt/backups/auth/
/opt/backups/api.py
/etc/systemd/system/backups-*.service
```
---

## 15.2. Восстановление сервера

Порядок:

1. Установить базовую ОС и зависимости.
2. Установить:
   - Python 3.8;
   - PostgreSQL;
   - `rest-server`;
   - `restic`;
   - 7z.
3. Распаковать архив в корень файловой системы.
4. Восстановить дамп PostgreSQL.
5. Проверить права на секреты.
6. Запустить `rest-server`.
7. Запустить `api.py`.
8. `api.py` проверяет репозитории и подключает клиентов.

# 17. Ограничения и дополнительные меры защиты

## 17.1. Ограничения `append-only`

`append-only` защищает от удаления и перезаписи данных клиентом через `rest-server`.

Он не защищает от:

- добавления мусорных данных;
- исчерпания места;
- локального удаления данных администратором сервера;
- компрометации сервера;
- ошибочного `prune`.

Дополнительные меры:

- квоты;
- мониторинг места;
- лимит снапшотов;
- контроль аномального роста;
- аудит;
- ограничение прав на сервере;
- файловые снапшоты СХД;
- резервные копии конфигурации и ключей.

---

## 17.2. Ограничения проверки целостности

`restic check` без чтения данных проверяет структуру и метаданные, но не гарантирует физическую читаемость всех блоков.

Для гарантии читаемости данных необходимо использовать:

```bash
restic check --read-data
```

или:

```bash
restic check --read-data-subset=<percent>
```

---

## 17.3. Один репозиторий на бэкап

Выбор «один репозиторий на каждый бэкап» является осознанным.

Следствия:

- больше репозиториев;
- больше паролей;
- больше операций обслуживания;
- выше изоляция;
- проще политики хранения для каждого бэкапа.

---

## 17.4. Сервер знает пароли репозиториев

Это принимается как требование модели доверия.

Следствие:

- сервер может проверять, чистить и восстанавливать данные;
- при компрометации сервера конфиденциальность данных не гарантируется.

---

## 17.5. Python 3.8

Использование Python 3.8 обязательно:

- в RedOS 8;
- в Windows 7 Pro.

# 18. Итоговые обязательные правила

1. Одновременно может быть запущен только один экземпляр одного бэкапа.
2. Нет команды `manager.hello`.
3. Нет клиентских команд удаления снапшотов.
4. Один репозиторий на каждый бэкап.
5. Клиент только пишет; восстановление только сервером вручную.
6. Конфигурация — в INI, оперативное состояние — в PostgreSQL.
7. Команды живут 12 часов, окно офлайна — 6 часов.
8. Максимальное время бэкапа — 12 часов.
9. Через 3 часа бэкап помечается как `long_running`.
10. Повторные попытки — до 5 раз с интервалами 5, 15, 30, 30, 30 минут.
11. Сетевые ошибки повторяются; ошибки доступа и скрипта — нет.
12. Удаление устаревших снапшотов только при наличии более нового успешного снапшота.
13. `prune` не выполняется автоматически после каждого `forget`.
14. `prune` обязателен не реже раза в сутки.
15. Вредоносный клиент не может удалить старые данные, но может пытаться заполнить место; это контролируется квотами и мониторингом.
16. Дампы баз данных не пишутся на диск, а передаются в `restic` через конвейр.
17. Кэш `restic` находится на отдельном диске, лимит 1 ТБ, при переполнении допускается работа без кэша.
18. Перед каждым запуском проверяется версия скрипта; при старой версии выполняется обновление.
19. Аварийное восстановление сервера выполняется через зашифрованный 7z-архив `/backups/restic_YYYY-MM-DD.7z`.
20. При старте `api.py` проверяет репозитории и подключает клиентов.
